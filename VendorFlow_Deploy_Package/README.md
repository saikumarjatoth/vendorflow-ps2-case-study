# VendorFlow — Vendor Onboarding & Review System

VendorFlow is a runnable Streamlit application for the vendor-onboarding case study. It accepts structured vendor submissions and tagged supporting files, executes eight visible review stages, produces an explainable APPROVED, PENDING or REJECTED outcome, drafts a vendor message, and stores the audit trail.

## Publish a public app URL

Follow **[DEPLOY_TO_STREAMLIT_CLOUD.md](DEPLOY_TO_STREAMLIT_CLOUD.md)** to publish this project through Streamlit Community Cloud. The app URL is created by the hosting provider after the project is uploaded to GitHub and deployed; it cannot be generated by converting `app.py` alone.

## Run it locally on a Mac

Requires Python 3.10 or newer. From Terminal, change to the extracted project folder, then run:

```sh
./run.sh
```

Open **http://localhost:8501** in Chrome. Stop the app with **Ctrl+C** in Terminal. First startup needs an internet connection to install Streamlit.

Alternative manual startup:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
streamlit run app.py
```

## What the app does

1. Receives structured company, tax and masked bank details plus supporting files.
2. Normalizes whitespace and uppercases PAN, GSTIN and IFSC.
3. Checks required fields, PAN/GSTIN structure and relationship, email and phone shape, IFSC shape, and last-four-only account entry.
4. Checks whether applicable, tagged documents are attached, and whether each uploaded file matches a supported extension, size and basic file signature.
5. Compares the legal business name with the bank account holder. Partial or absent name overlap needs human review.
6. Checks an active local vendor master for duplicate identifiers.
7. Applies deterministic decision rules and shows the reason and next action.
8. Prepares a communication draft and records each run.

## Decision rules

- **APPROVED:** required fields and applicable documents are present; configured formats pass; bank and legal names align after punctuation and legal-suffix normalization; no duplicate is found.
- **PENDING:** an item is missing or malformed, a name needs clarification, a possible duplicate is found, or an uploaded file fails basic validation.
- **REJECTED:** both PAN and GSTIN match one active record. This is a duplicate-record outcome, not an accusation of fraud. A one-identifier or name-only match stays PENDING for review.

Registration number and registration document are required for private/public companies, LLPs and partnerships in this demo. PAN proof and bank proof are always required. A GST certificate and GSTIN are required when GST status is Registered. Proprietorships do not have a registration-number requirement here.

An approval inserts the vendor into the local active master. A later identical submission is therefore treated as a duplicate. Use **Reset demo dataset** to clear run history and uploaded files and restore the seeded active demonstration vendor.

## Try the sample cases

On the Dashboard, load one of the four synthetic examples, review/edit it in New Submission, then click **Submit and run review**:

| Scenario | Expected outcome | Demonstrates |
| --- | --- | --- |
| Successful Vendor | APPROVED | Complete, consistent details |
| Missing Documents | PENDING | Missing bank proof and exact next request |
| Bank Details Mismatch | PENDING | Human clarification without a fraud conclusion |
| Duplicate Vendor | REJECTED | Exact PAN + GSTIN match to seeded active vendor |

Sample files are plain-text placeholders marked **DEMONSTRATION ONLY — NOT AN OFFICIAL DOCUMENT**. They exist only to demonstrate document-presence checks; they do not resemble or claim to be real government or bank documents.

## Test the rules

```sh
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

The test suite exercises all four scenarios through the business engine plus invalid identifiers, missing information, missing documents, unsupported/mislabeled uploads, malformed JSON, full bank-number rejection, ambiguous name review, partial duplicate routing and repeated approved submissions. The included `TEST_RESULTS.md` records the last test execution.

## Data storage and privacy

Local data lives in `data/vendorflow.sqlite3`. Runs, the active demo vendor master and uploaded file bytes are stored in SQLite. Do not use real vendor tax identifiers, banking documents or personal information in this demonstration app. Use only the final four digits of an account number. Override the database location with `VENDORFLOW_DB=/path/to/vendorflow.sqlite3`, or set `VENDORFLOW_DATA_DIR=/path/to/data-directory` before launch.

The deploy package deliberately excludes the local SQLite database so that a hosted demo starts with a clean synthetic vendor master. Hosted local-file storage is not durable; run history and uploaded files may be cleared on restart or redeploy.

## Project files

- `app.py` — Streamlit interface, dashboard, forms and live stages.
- `vendorflow/rules.py` — normalization, validation, decision logic and communication drafts.
- `vendorflow/storage.py` — SQLite schema, run history and vendor master.
- `vendorflow/samples.py` — synthetic sample submissions and seeded vendor.
- `demo/sample_documents/` — clearly labeled placeholder attachments.
- `tests/` — automated business-rule tests.
- `DEMO_SCRIPT.md` — five-minute narration, screen sequence and rehearsal notes.
